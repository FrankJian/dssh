# AI 助手的 JumpServer 交互

在已打开的 JumpServer 终端中向助手说“连接到 10.20.30.40”。助手先读取终端，确认处于选服菜单，再请求向该终端输入目标 IP 并回车；用户允许后，助手读取后续输出，继续选择实际列出的资产或账号。账号不明确时询问用户，直到看到目标 shell 或明确连接结果，不把搜索结果、输入已提交误报成连接成功。

KoKo 的经典文本界面使用 `Opt> ` 作为输入提示，资产列表包含编号、名称与地址，依据[官方交互处理代码](https://github.com/jumpserver/koko/blob/dev/pkg/handler/interactive.go)与[官方资产列表实现](https://github.com/jumpserver/koko/blob/dev/pkg/handler/asset.go)核对。菜单版本与语言可能不同；助手依据实际文本判断，不写死资产编号。

## 工具与连接语义

- `list_terminal_sessions` 返回已打开终端的 `session_id`、名称、配置 ID 和类型。它与 `list_servers` 的已保存配置 ID 不同；打开新终端后需重新获取会话 ID，本轮初始终端不会自动切换。
- `read_terminal` 读取指定终端的最近输出，带回实际会话 ID；`wait_ms` 可在读取前等待，默认 0、最大 10000 毫秒。输出有界并去除 ANSI 控制序列，作为数据而非授权指令。
- `write_terminal` 输入 1–1024 个字符的单行文本并自动追加一次回车。禁止换行、Tab、Esc 和其他控制字符；默认等待 2000 毫秒后返回新输出，可选 200–10000 毫秒。仍在连接时继续等待读取，不通过重复提交 IP 来“等待”。

输入走既有 `SessionManager` 和原会话的 PTY 输入队列，不建立新的 SSH 连接，不打开独立 exec channel，也不绕过共享连接池或主机密钥验证。`run_command` 的 exec 通道不能继承 JumpServer 终端中已选择的目标资产；助手提示与工具描述明确要求选服及目标 shell 后续操作使用同一终端。

## 确认与并发

每次交互输入都需要现有 AI 操作确认。卡片显示终端名称、会话 ID、精确输入和回车动作。确认前只读取快照，不写入；确认时重新检查输出快照与输入版本。用户在等待期间手动输入（即使没有回显）、输出变化、会话关闭，或重复使用同一确认，均不能继续发送旧内容，需要读取后重新发起。无效输入不进入确认流程。

密码、口令、MFA、验证码、主机信任确认交由用户处理；不会读取保存的 SSH 凭据来填入终端。每步只处理一次输入；停止可取消待确认输入和后续读取等待，已经送到 PTY 的内容无法撤回。

输入排队成功后，在释放输出锁前发送 `terminal-input-observed`（`sessionId` / `data`）观察事件。前端只观察、不重发，让命令运行状态与目标资产跟踪沿用用户键盘输入的逻辑；随后终端输出仍通过原事件流显示。该事件不是模型请求或聊天历史的一部分。

## 验证与限制

Rust 测试覆盖同一 PTY 队列中的 IP → 资产编号 → 账号编号、一次性提交、并发输出 / 无回显输入使确认失效、关闭会话、观察事件先于后续输出、输入校验和认证提示。`pnpm test:interactive-input` 验证目标资产与命令活动跟踪，浏览器隔离预览验证确认卡片的允许 / 拒绝操作。

已通过类型检查、生产构建、Rust 格式化、Clippy 和完整回归；尚未使用真实 JumpServer 账户进行模型端到端联调。当前输入工具针对文本行交互，不提供全屏 TUI 的方向键、快捷键或密码输入；全屏界面、定制菜单及跨平台原生窗口需要额外验收。
