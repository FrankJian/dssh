# 0.6.30 长时间 tail 后 Ctrl+C 无效的排查

> 旧版本排查记录；当前输出行为见 terminal-output 主规格，不据此宣称问题已全部解决。
> 来源：`docs/terminal-tail-interrupt-0.6.30.md`，整理于 2026-11-21。保留原文时间与验收限定语。


2026-11-21 后续：当前工作区已实现消费确认和有界输出/过载暂停，见[实现与验收范围](../architecture/terminal-output-flow-control.md)。以下是对 0.6.30 / 0.6.31 的原始排查记录；不能据此认为新方案已经随旧版本发布。

## 当前结论

不能认定已全面修复，也尚未复现用户的整夜 SSH/Windows 现场。对比了 `v0.6.30`（49cf50d）、`v0.6.31`（a78564d）及当前工作区：0.6.31 改善了历史缓冲、文本追踪和多窗口 IPC，但实时输出仍直接调用 `terminal.write(data)`，没有端到端输出流控。升级不能作为此故障已解决的证明。

代码中没有发现按“运行一晚/一天”自动禁用 Ctrl+C 的逻辑。SSH PTY 请求指定 `VINTR=3`、`ISIG=1`，普通输入仍通过 `write_ssh_session` 发送。前台任务可更改远端终端模式，因此这也不代表远端必然会将每个 `0x03` 转成 SIGINT。输出事件率的 debug 统计位于 `cfg(debug_assertions)` 中，正式 release 不编译它；没有证据把故障归因于该统计。

## 确认的问题与本次改动

1. **选区持续拦截中断。** 0.6.30 / 0.6.31 的复制快捷键遇到选区就返回 false，选区却保留。默认 Windows Ctrl+C 因此可以连续只复制，始终不产生中断字节。当前补丁保留第一次复制，并清除选区，让下一次 Ctrl+C 进入输入路径；同时阻止默认复制动作，处理剪贴板 Promise 失败。仅在实际匹配复制快捷键时生效，保留自定义绑定。
2. **中断发送失败缺少用户提示。** 后端输入队列容量 256，使用 `try_send`；队列已满或会话关闭时会拒绝输入。原前端只写 console.error，用户只能看到“没反应”。当前补丁为含 `0x03` 的发送失败增加通知；通知表示调用失败，不把“进入队列”误说成远端已经停止。
3. **待绘制队列尚无流控。** 已保留的 200 KB 历史与 xterm 的 5,000 行滚动历史都不限制尚未解析的输出。安装的 xterm `WriteBuffer` 在待处理量超过 50,000,000 字符后拒绝后续写入，项目目前没有处理这一路异常或向生产者传播消费确认。不能通过任意丢弃 ANSI 字节或暂停一个共享 SSH transport 的 channel 消费来修复。

前两项是确定的客户端行为缺口，但没有用户现场证据证明它们就是这次整夜故障的原因。第三项仍未修复：需区分 UI 处理输入延迟、远端没收到中断、远端已经停止但客户端仍在显示历史积压。

## 可复现证据与边界

```sh
node scripts/diagnose-terminal-flood.mjs
node scripts/diagnose-terminal-flood.mjs --overflow
```

通过项目实际安装的 xterm 公共 API，有限突发测试得到：

- 8,000,000 字符已入队、尚未解析时，`terminal.input("\x03", true)` 立即触发 `onData`，带出中断字节。证明输入事件处理函数一旦能够执行，并不必等待旧输出解析完。
- 50,016,000 字符已入队时，下一次 write 抛出 `write data discarded, use flow control to avoid losing data`。5,000 行滚动上限不能阻止此问题。
- 两种场景已接受的输出最终都解析完。单纯触及阈值不等于永久卡死，不能从该异常直接推断用户的故障根因。

这是 Node 下无 DOM、无 SSH、无 WebView 的解析器诊断，不是 Windows 吞吐、键盘时延或 24 小时 soak 测试。脚本不读取实际日志、不连接主机、不发送远端命令。本次 TypeScript 和生产构建通过。隔离浏览器验收尝试受本地浏览器访问不可用、原生 Chrome 窗口不可用和沙箱监听限制影响，没有完成；临时页面/基线副本已清理，选区行为补丁仍需原生键盘验收。

## 用户现场最有价值的区分

- 先单击终端取消文字选区，再按 Ctrl+C：若随即恢复，优先确认复制拦截。
- 若菜单、标签切换和键盘都显著变慢，记录 Windows/WebView2 版本、Duo SSH 和 WebView 进程内存、输出速率，优先排查 UI/IPC 积压。
- 若界面操作正常但持续刷屏，需要从另一条连接只读确认原 tail 进程是否仍在，区分远端尚未停止与本地正在排空积压。不要先关闭会话或强杀进程而丢失现场。

发布验收仍需使用 Windows 正式包，覆盖无选区/有选区的重复 Ctrl+C、稳定低速长跑、高速突发、多窗口，以及输出洪水期间的中断与其他 SSH channel 可用性。两项小补丁不能代替端到端流控或上述实机验收。
